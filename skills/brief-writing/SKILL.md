# 技术简报写作（解释型）

## 目标
读者是**第一次接触这个主题的人**。读完这份简报，他应该能回答：
- 这是什么？属于哪个领域？
- 为什么需要它？没有它会怎样？
- 它怎么运作？
- 实际用起来要注意什么？

简报**不是证据台账**。核验是写作前的质量把关，不是简报的内容。

## 结构（固定）
1. 一级标题＝主题名
2. **一句话定义**：是什么 + 所属领域 / 解决什么问题（≤60 字）
3. **为什么重要**：2 句，讲它替代了什么、解决什么痛点
4. **怎么运作**：2~3 点，每点「小标题 + 一句解释」，**要写出具体机制或步骤**
   （如「写入—存储—召回—注入」的链路，或「短期缓冲 / 长期存储」的层次），不要只写作用
5. **实践要点**：2~3 条**具体可操作**的做法或选型判断，避免「需结合场景」这类空话
6. 「来源」小节（链接列表，**不计入** 500 字）

## 长度预算
- 正文**目标 380~420 字**，硬上限 460 字；宁可少写一条实践要点，也不要超限
  （超限会触发一轮重写压缩，既慢又容易把结构压平）
- 压缩时**必须保留小标题与分点层级**，只压缩各段内部文字

## 语言
- 平实、少术语；必须出现的术语紧跟一句解释
- 多用「它解决了…」「做法是…」「代价是…」这类陈述
- 少用「某资料称…」「据报道…」这类转述——直接说内容，把出处留给来源小节

## 核验的正确位置
- 核验结果**不单独成段**，只在需要时以括注体现
- 全文允许 **1~2 处**括注存疑，例如「（该数值待核实）」
- 禁止出现「核验结论」「证据强度」「单一来源」「待核实」这类成段论述

## 字数控制
- 正文（不含一级标题与「来源」小节）≤ **500 字**
- 中文口径：去 Markdown 语法（链接保留文字）、去空白后的字符数

## 压缩策略（超限时按序执行）
1. 删修饰语与程度副词（「非常」「显著」「在很大程度上」）
2. 合并同类要点（3 条同义并为 1 条）
3. 删次要例证，只留主干
4. 仍超限则缩为「定义 + 3 点运作 + 1 句小结」

## 禁止
- 不得删除来源链接
- 不得把未核验内容写成确定语气（用一句括注即可）
- 不得用「资料不足」占篇幅——说不清的部分直接略过

## 输出
Markdown 简报全文，含一级标题、五个部分与「来源」小节。
